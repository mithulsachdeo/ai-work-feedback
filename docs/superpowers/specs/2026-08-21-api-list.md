## 1. `POST /api/evaluate` — the core engine

**Need:** this is the product. A user submits work; this route turns it into scored, teaching feedback.

**Logic, in order:**
1. **Auth-gate.** Resolves the Supabase session from cookies; 401 if not signed in.
2. **Validate input.** `text` must be ≥20 chars (400 if not); `intent` must be non-empty (400 if not — added so the purpose/text-mismatch guardrail always has something to compare against). Text over `MAX_SUBMISSION_CHARS` is truncated with a `truncated` flag returned to the UI, not silently dropped.
3. **Validate BYO provider**, if a key was supplied — must be one of `gemini`/`anthropic`/`openai`, else 400.
4. **Quota gate (free tier only).** Reads `getRemaining(user.id)` *before* doing anything expensive; 429 if zero. BYO-key requests skip this entirely.
5. **Ownership check on `previousSubmissionId`.** If the client claims this is a resubmission, `getSubmissionOwner` verifies that submission actually belongs to the caller before trusting it for lineage — silently ignored (not an error) if it doesn't match, since content tables have no database-level RLS to fall back on.
6. **Call the model.** `evaluate()` builds the rubric prompt (including the dual-capture `originalDraft` block and the `role` context, both fenced against injection) and calls the chosen provider. Retried once **on the LLM call only** — not on the DB writes below, so a transient failure can't create duplicate rows.
7. **Persist, but only after success.** Writes `submissions` (with `original_draft`, linked via the *verified* previous-submission id) then `evaluations`.
8. **Measurement loop.** If the result is scored (not `not_evaluable`) and linked to a verified previous submission, compares levels via `improvedAny` and writes a `resubmitted` outcome row.
9. **Charge quota only on a genuine scored success** — never on `not_evaluable`, so a bad/gibberish submission doesn't cost the user a daily check.
10. **Track + respond.** Fires `evaluation_completed` (and `level_improved` if applicable) to PostHog, returns `{ evaluationId, submissionId, result, remaining, truncated, improved }`.

## 2. `POST /api/ask` — side-questions channel

**Need:** lets a user ask a quick question about their current work/feedback without leaving the app or turning the tool into a general-purpose assistant.

**Logic:**
1. Auth-gate (same pattern as above).
2. Validate `question` present, and size-cap both `question` (≤1000 chars) and `context` (≤2000 chars) — it's meant to be a quick question, not a document.
3. Validate BYO provider the same way as `/api/evaluate`.
4. **No quota check** — deliberately decoupled from the daily evaluation counter (a first session of submit + a couple questions could otherwise burn most of a new user's 10 daily checks before they've even explored the product). Guarded instead by the auth-gate + length cap, since each call is cheap relative to a full evaluation.
5. Calls the model with a **scoped system prompt**: answers only questions about the user's current submission, their feedback, or improving AI-assisted work — declines and redirects anything off-topic ("do my homework," general knowledge, unrelated coding).
6. Returns `{ answer }`; on failure, a friendly 502.

## 3. `POST /api/outcome` — behavioral gold-signal writer

**Need:** the north-star metric needs ground truth on what users actually *did* with feedback, not just that they received it.

**Logic:**
1. Auth-gate.
2. Validates the request is exactly `{ evaluationId, action: "viewed_fix" }` — this route only ever writes this one action type; `resubmitted` is written directly by `/api/evaluate` since that's the moment it's actually knowable.
3. Writes a `feedback_outcomes` row. **No ownership check on `evaluationId`** — a deliberate, documented accepted risk (write-only, no data read back, worst case is a wrong analytics count at friendly-tester scale).

## 4. `GET /api/last-submission` — cross-session resume

**Need:** identity and data both persist across sessions (magic-link auth), but without this route there's no way for the browser to ask "what did I last submit?" — content tables have zero browser-facing RLS policy, so this data is otherwise unreachable from the client.

**Logic:**
1. Auth-gate.
2. Calls `getLastSubmission(user.id)`, which fetches the user's most recent `submissions` row, then its most recent linked `evaluations` row.
3. **Fails silent (`null`)** in three cases: no submission exists yet, the last one was `not_evaluable` (nothing meaningful to resume into), or it was saved with `doNotStore` (no real text was kept). A dead-end "continue" button would be worse than none.
4. Returns `{ last: LastSubmission | null }`; the client shows a "Continue your last check" banner only when non-null.

## 5. `GET /auth/callback` — magic-link session exchange

**Need:** the bridge between "user clicked the emailed link" and "user has an active session" — not really product logic, but required infrastructure for auth to work at all.

**Logic:**
1. Reads the `code` query param from the magic-link redirect.
2. Exchanges it for a session via `supabase.auth.exchangeCodeForSession(code)`, using the full `get`/`set`/`remove` cookie handler set (this route is actually where that pattern originated — the other routes above were later fixed to match it).
3. Redirects to `/app`.

## Cross-cutting design choices (apply to all five routes)

- Every route re-derives the Supabase session from cookies independently (no shared middleware) — simple, if slightly repetitive.
- Only `/api/evaluate` and `/api/ask` touch the LLM providers; only `/api/evaluate`, `/api/outcome`, and `/api/last-submission` touch content tables, always via the service-role client — the anon/cookie-based client is used solely for the `auth.getUser()` check, never for content reads/writes.
- Every route fails toward a clear, user-facing error message rather than a raw stack trace — consistent with the guardrails principle that a broken parse or provider timeout should degrade gracefully, not crash the UI.
